# Safe Change Playbook

This reference expands the `refactor` entry point for transformations whose risk crosses several files,
runtime boundaries, generated artifacts, public APIs, or persistent data.

## Decision packet

Before editing, write a compact packet:

```text
Target:
Structural outcome:
Observable behavior preserved:
Explicit non-goals:
Consumers:
Baseline commands:
Real scenario:
Migration order:
Rollback:
```

If this cannot be written from repository evidence, the refactor is not ready.

## Dependency map

Build a directional map:

```text
input boundary
  -> parser or adapter
    -> domain owner
      -> side-effect port
        -> external system
```

Add package exports, generated inputs, configuration, persistence, user documentation, and tests beside the
node they constrain. Mark cycles and import-time side effects. A file list without direction is not a
dependency map.

For each proposed move, answer:

- Who owns the invariant after the move?
- Which layer may depend on which?
- What public surface remains?
- What construction or initialization order changes?
- Which error and cancellation path crosses the new seam?

## Compatibility strategies

### Atomic internal change

Use when all consumers are inside one repository and can migrate in one checked patch. Keep the diff
coherent and verify the built or packaged form.

### Add, migrate, remove

Use when consumers can be migrated in stages:

1. add the new surface;
2. delegate from the old surface without changing behavior;
3. migrate known consumers;
4. prove the old surface has no remaining in-scope use;
5. remove it only when compatibility authority allows.

### Dual read or dual write

Use only for persistent-data migrations with an explicit consistency rule. Define which representation is
authoritative, how divergence is detected, deploy order, backfill, rollback, and when the dual path ends.
Dual write without reconciliation creates two sources of truth.

### Versioned boundary

Use when external consumers cannot migrate atomically. Preserve the old version, add the new contract, and
define support and removal criteria. Do not smuggle a breaking change into a refactor label.

## Generated artifacts

Classify each generated file:

- **authoritative output** — always regenerated, never hand-edited;
- **checked-in output** — regenerated by a named command and reviewed;
- **template/input** — source of truth to edit;
- **cache/build product** — ignored and removable.

Find the generator and deterministic invocation before touching checked-in output. If generation changes
unrelated regions, stop and explain the drift rather than accepting noise.

## Error preservation

Refactoring often changes errors accidentally. Compare:

- error type or code;
- cause chain;
- message contract when user-visible;
- exit status or HTTP status;
- retryability;
- partial side effects;
- logging ownership;
- cancellation versus failure.

Test at the outward boundary. Internal exception classes are not the contract unless callers observe them.

## Ordering and side effects

Extraction and movement can change:

- evaluation order;
- lazy versus eager work;
- lock acquisition;
- transaction boundaries;
- initialization timing;
- event emission;
- resource lifetime;
- retry scope.

Write an event or state sequence for high-risk paths before and after. Equivalent final values do not prove
equivalent behavior when intermediate effects matter.

## Performance preservation

When performance is part of the contract, capture comparable before/after evidence:

- same build mode and runtime version;
- same dataset and warmup;
- distribution, not one timing;
- allocations or resource counts when relevant;
- correctness check on benchmark output.

A faster result obtained by skipping validation, cancellation, durability, or cleanup is a regression.

## Review matrix

| Question | Evidence |
| --- | --- |
| Did all intended consumers migrate? | semantic result when available plus scoped searches |
| Did public names remain compatible? | package/API/CLI/config inspection and scenario |
| Did runtime loading still work? | run the built or packaged artifact |
| Did errors remain stable? | failure-path scenario |
| Did concurrency ownership remain safe? | race/schedule tool and cancellation scenario |
| Were generated files handled correctly? | generator command and clean follow-up run |
| Can the step be reversed? | explicit owned rollback without destructive repository reset |
| Is temporary state gone? | process, port, temp, config, and diff receipt |

## Failure response

At the first unexplained regression:

1. stop later slices;
2. preserve the failing command and output;
3. identify the earliest slice that introduced it;
4. revert or correct only that owned slice;
5. rerun the baseline and the failing scenario;
6. update the plan before resuming.

Do not pile fixes onto an unbounded broken state. Do not reset or clean the repository to recover.
